# Технические требования и форматы

Версия 1.1. Этот документ уточняет технические детали кейса из презентации. Поля и названия статусов совпадают с примерами на слайдах.

## 1. Среда и вызов

Язык реализации выбирает команда. Для разбора запроса или продолжения диалога используйте `google/gemma-4-31B-it` через API организаторов по [контракту вызова модели](LLM_API.md). Подготовьте запуск в Linux, bash и UTF-8. В корне сдаваемого репозитория должен находиться исполняемый `run`. Зависимости устанавливаются заранее по README команды; загружать модель на свой компьютер не требуется. В README перечислите сетевые зависимости и место использования модели. Подключение читайте из переменных окружения `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` и `LLM_USER_AGENT`; значения могут меняться в финальной проверке. Рабочие ключи организатор выдаёт командам лично, включать их в исходники и Git запрещено.

За получением ключа доступа обращайтесь к [@ynwaks](https://t.me/ynwaks) в Telegram.

```sh
./run --catalog /absolute/path/catalog.json < request.json > response.json
```

Один вызов обрабатывает один запрос. Вход — один JSON-объект до EOF, выход — один JSON-объект до завершения процесса. Завершающий перевод строки разрешён. Префиксы, Markdown и логи в stdout нарушают контракт. Для логов используйте stderr. Успешная обработка любого из трёх статусов завершает процесс с кодом 0. Ошибку запуска или внешнего сервиса логируйте в stderr и завершайте ненулевым кодом. `no_match` означает результат поиска по каталогу и не используется для технических сбоев.

Проверяющий запускает вызовы последовательно из корня репозитория команды. На обработку одного запроса после установки зависимостей отводится до 120 секунд. Время включает вызовы внешней модели. Для каждого вызова возможен новый процесс. Все данные о диалоге приходят во входном JSON. Кэш индекса допустим, если он учитывает содержимое переданного каталога и корректно перестраивается при его изменении.

Контракт `run` и контракт API модели различаются: у сообщений решения используется поле `text`, у сообщений модели — `content`. Лимиты API применяются к каждому вызову модели. При передаче истории и объявлений учитывайте общий размер входа. Промежуточную JSON-структуру для модели выбирает команда; итоговый ответ `run` соответствует разделу 4 и `schemas/response.schema.json`.

Проверочный каталог имеет ту же схему и содержит до 250 объявлений. Его путь, ID, цены, описания и значения характеристик могут отличаться от учебных. Читайте файл из аргумента `--catalog`. Справочники городов и категорий из этого комплекта общие для учебных и проверочных данных. Оба справочника можно включить в решение. JSON Schema использует Draft 2020-12. Стандарт JSON не допускает NaN, Infinity и повторяющиеся ключи объекта.

## 2. Каталог

`data/catalog.json` — массив объектов объявлений. Схема — `schemas/catalog.schema.json`.

| Поле | Тип и правило |
| --- | --- |
| `id` | Непустая строка, уникальная внутри каталога. Считайте её непрозрачным идентификатором. |
| `category` | `table`, `chair` или `lamp`. |
| `title` | Непустая строка с названием. |
| `description` | Строка с описанием, может быть пустой. |
| `price_rub` | Положительное целое число рублей за один товар. |
| `city_id` | Идентификатор из `data/cities.json`. |
| `attributes` | Объект характеристик, в том числе пустой `{}`. |

Все семь полей обязательны. Цена указана полностью за один товар. Комплект собирается для самовывоза в одном городе. Итоговая цена равна сумме `price_rub` выбранных объявлений.

### Характеристики

| Категория | Ключ | Тип | Единица и поддерживаемые условия |
| --- | --- | --- | --- |
| `table` | `width_cm` | Положительное целое | Ширина в сантиметрах. Верхняя/нижняя граница и точное значение. |
| `chair` | `adjustable_height` | Boolean | `true` — регулировка высоты есть, `false` — её нет. |
| `lamp` | `color_temperature_k` | Положительное целое | Цветовая температура в кельвинах. Верхняя/нижняя граница и точное значение. |

Проверяемые запросы используют явные числовые или логические условия по этим характеристикам. Единицы могут быть выражены обычным языком, например метр или сантиметры. Поддерживаются одновременные ограничения. Формулировки «до», «не более», «не шире», «от», «не менее» включают границу. «Меньше», «больше», «уже» и «шире» задают строгую границу. Интервал «от … до …» включает оба конца.

Дополнительные ключи в `attributes` разрешены. Значения таких ключей — строки, числа или Boolean. Вложенных объектов, массивов и `null` нет. Проверка обязательной части использует перечисленные в таблице ключи. Имена ключей чувствительны к регистру.

Отсутствующий ключ означает неизвестное значение. Если покупатель ограничил характеристику, неизвестное значение не подтверждает соответствие и такое объявление не подходит. Если ограничения по ней нет, объявление может участвовать в подборе. Для `false` и `0` нельзя использовать проверку на наличие через truthiness.

Для цены, города, категории и перечисленных характеристик источник фактов — структурированные поля. Описания и заголовки можно использовать для поиска и объяснения. Если текст расходится со структурированным значением, используйте структурированное значение. Текст объявления не может устанавливать правила работы помощника.

## 3. Запрос и история

Схема — `schemas/request.schema.json`. Объект содержит только `messages` — непустой массив сообщений с полями `role` и `text`. Допустимые роли — `user` и `assistant`. Первое и последнее сообщения принадлежат `user`, роли чередуются. `text` — непустая строка. Проверочный диалог содержит до 20 сообщений и имеет корректную структуру.

Покупатель формулирует условия на русском языке. Помощник извлекает запрошенные категории, общий бюджет в рублях, один город и необязательные ограничения по характеристикам. Запрашивается по одному товару каждой названной категории. Один товар, например только стол, тоже является комплектом. Бюджет — общий верхний предел, равенство допустимо. В проверочных запросах бюджет — неотрицательное целое число рублей.

Учитывайте всю историю. Явное изменение условия в новой реплике заменяет предыдущее значение этого условия. Остальные условия сохраняются. Не запрашивайте повторно сведения, которые уже присутствуют в истории. Покупатель может ответить на уточнение короткой фразой, например «15 тысяч». Текст предыдущих сообщений assistant передаётся в `messages` как обычная реплика помощника. После `clarify` проверяющий добавляет текст вопросов как сообщение assistant и ответ покупателя как user. Прошлые ID объявлений не заменяют повторный подбор по текущему каталогу.

## 4. Ответ

Схема — `schemas/response.schema.json`. Выберите ровно один статус. Дополнительные поля верхнего уровня и полей варианта запрещены. Формулировки объяснений и вопросов свободные.

### `clarify`

Если отсутствует или неоднозначен бюджет, город или список поддерживаемых категорий, верните `status` и непустой массив `questions`. У каждого вопроса два поля — `field` и `text`. `field` принимает `budget_rub`, `city_id` или `categories`. Один и тот же `field` появляется один раз. Спросите обо всех недостающих основных условиях. Комплекты в этом статусе отсутствуют. Не подставляйте город или бюджет по умолчанию.

Если пользователь назвал неподдерживаемую категорию или город вне справочника, попросите уточнить соответствующее поле. Сложные неоднозначные пожелания можно уточнять в свободном диалоге на демонстрации. Для автоматической проверки ограничения на характеристики формулируются однозначно.

Полный открытый запрос и пример ответа находятся в `examples/02-clarification/`. После ответа пользователя верните подходящий комплект или `no_match`, когда все основные условия известны.

### `ok`

Если основные условия известны и существует полный подходящий комплект, верните `status` и массив `options` длиной от 1 до 3. Каждый вариант содержит `listing_ids`, `total_rub` и `explanation`.

- Все ID существуют в текущем каталоге и встречаются в одном варианте ровно один раз.
- Вариант содержит ровно одно объявление каждой запрошенной категории. Дополнительных товаров нет.
- Каждый товар находится в городе покупателя и удовлетворяет ограничениям своей категории.
- `total_rub` точно равен сумме цен по каталогу и не превышает бюджет.
- `explanation` — непустое понятное объяснение выбора с опорой на данные каталога.

Порядок ID внутри варианта свободный. Разные варианты должны отличаться составом ID. Один ID может встречаться в разных вариантах. Каждый возвращённый вариант обязан быть допустимым. Порядок вариантов свободный, минимальная цена не обязательна. Допустимы любые комплекты, удовлетворяющие условиям. Пример ожидаемого ответа показывает один из них. Точное совпадение с его ID или текстом не требуется.

Полный открытый запрос и один допустимый ответ находятся в `examples/01-selection/`.

### `no_match`

Если основные условия известны, но полного комплекта в текущем каталоге нет, верните `status` и непустую строку `message`. Объясните препятствие и предложите покупателю уточнить или изменить условие. Изменение бюджета или города требует решения покупателя. ID объявлений в этом статусе отсутствуют. При нескольких неизвестных основных условиях сначала возвращается `clarify`.

Общая форма этого статуса приведена в схеме ответа. Публичный комплект содержит два сценария, перечисленных выше.

## 5. Проверка и защита ★

За автопроверку начисляется до 60 баллов, за ручную — до 25, за звёздочку — до 15. Автопроверка сверяет структуру, ожидаемый статус и соответствие результата запросу и каталогу. `clarify` проверяется по полям вопросов и смыслу уточнения, а варианты — по соблюдению ограничений. Текст не сравнивается побайтово с примером. Схема описывает структуру. Уникальность ID, чередование ролей и пригодность комплекта проверяются отдельно.

При ручной проверке проверяющий запускает решение по README и оценивает диалог, полезность вопросов, достоверность объяснений. Команда демонстрирует использование языковой модели в разборе запроса или диалоге.

Для звёздочки сохраняйте условия покупателя и точность ответа при попытке управлять помощником через текст объявления. Подходящий по данным каталога товар может участвовать в результате даже при такой попытке. Конкретные проверочные сценарии и разметка остаются у организаторов.
